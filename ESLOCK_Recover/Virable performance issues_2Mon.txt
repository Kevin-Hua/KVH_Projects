**Root cause:** the AMI NVAR format uses a linked-list for variable updates, not repeated standalone entries. When `SetupChecksumList` is written 5 times:

- The first write is the **HEAD entry** (`NVAR_DATA=0`) — contains name, GUID index, and data
- Writes 2–5 are **data-only chain entries** (`NVAR_DATA=1`, `attrs=0x88`) — contain only the new data payload, no name
- Each entry's **Next** field (3 bytes at header offset 6) is a *relative offset from the current entry's start* pointing to the next in the chain; `0xFFFFFF` marks the last (current) entry

The old parser skipped all `NVAR_DATA` entries, so only the HEAD was shown. The new `_parse_nvar_store` follows the `Next` chain from each named HEAD entry, collecting all linked data-only updates and emitting them all as instances of the same variable. The tree now shows:

User: is it safe to use the smaller size to replace the variable ?

GitHub Copilot: In the NVAR format it is **not directly safe** — the `Size` field (bytes 4–5 of the entry header) is what tells the BIOS where the next entry begins. If you write fewer bytes without fixing that field, the BIOS parser will misread all subsequent entries in the store.

There are two practical ways to make it work safely:

**Option A — Pad new data to original data size (recommended)**
Keep the entry exactly the same total size; pad the end of the new data section with `0xFF`. The entry header (`Size`, name, GUID, ext-header) is untouched, the store layout is unchanged, and the BIOS sees a valid entry with zeroed-out trailing bytes.

**Option B — Shrink the entry and fill the gap with 0xFF**
Update the `Size` field to the new smaller size, then fill the freed bytes with `0xFF`. This works only when the freed space is at the *end* of a chain (no other entry points into it via a relative `Next` offset). It can leave orphaned 0xFF slabs mid-store that some BIOS parsers handle poorly.

User: is main the active nvram ?

GitHub Copilot: Yes. In UEFI firmware, the **Main Store** is the active (primary) NVRAM store. Here's how it works:

- **Main Store** — the active store where firmware reads and writes variables at runtime. Valid variables here are the currently active values.
- **Backup Store** (also called "Default" or "Spare") — a mirror/fallback copy used for recovery if the main store is corrupted. It typically holds the factory defaults or a known-good snapshot.

In the NVAR layout (AMI/Aptio), the partition header identifies which store is Main vs Backup. The firmware always boots from and writes to the Main Store. When NVRAM GC (garbage collection) runs, it compacts the Main Store by copying only Valid variables and erasing the rest.

So in your browser:
| Store | Purpose |
|---|---|
| **Main Store** | Active — runtime R/W, current variable values |
| **Backup Store** | Read-only fallback — factory/default values |

If you see a variable as `Valid` in Main Store, that is the value the OS/firmware is actually using.
